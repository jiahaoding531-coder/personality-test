# MVP V0.1 范围与验收标准

## 核心假设

> 用户完成一组人格测试 → 系统计算人格画像 → AI 根据画像生成个性化反馈

V0.1 的目标**不是**做出完整产品，而是用最小成本让这条链路真实跑通。

|---|---|---|

### ❌ 本轮不做

| 不做 | 原因 |
|---|---|
| React 前端 | 演示页已能验证完整流程；React 版的字段契约已固定，但需要 npm 与构建链，留到 V0.2 |
| 真实 AI 调用 | 接口已预留，V0.2 换个实现类即可 |

| 自训练模型 | 20 道题的规模，规则计算比模型更可靠 |
| 生产级部署 | 本机跑通优先 |
| 缓存 / 消息队列 | 个位数用户量，没有性能问题 |

## 为什么是这个范围

三条原则（来自计划书）：

1. **先证明核心价值，再扩大技术复杂度。**
   一个跑通的闭环比十个半成品模块有价值。

2. **不要让技术选型先于需求。**
   V0.1 的数据量（20 道题、个位数并发）用最简单直接的方案就够。
   提前引入缓存、消息队列、微服务只会让调试成本翻倍。

3. **不要为了"完整"建几十张表。**
   6 张表，刚好覆盖当前链路需要的信息。

## 验收标准

### 自动化验收

```bash
cd backend && ./mvnw test
```

期望：`Tests run: 79, Failures: 0, Errors: 0, Skipped: 0`

| 层 | 数量 | 需要数据库 | 覆盖 |
|---|---|---|---|
| 纯逻辑单元测试 | 19 | ❌ | 计分算法、提示词约束 |
| 集成测试 | 60 | ✅ | HTTP 契约、安全规则、事务、用户隔离 |

集成测试需要一个测试库（`personality_mvp_test`），
表结构由 Flyway 在测试启动时自动创建。详见 `CONTRIBUTING.md`。

### 端到端验收

启动后端后，用 `api.http` 依次执行：

- [ ] ① `GET /api/health` → `status: UP`，`questionCount: 20`
- [ ] ② `GET /api/questions` → 返回 20 道题 + 5 个量表选项
- [ ] ③ `POST /api/test-sessions` → 返回 `sessionId`
- [ ] ④ `POST .../answers` → `savedCount: 20`
- [ ] ⑤ `POST .../submit` → 返回 5 个维度的分数
- [ ] ⑥ `GET .../result` → 内容与 ⑤ 一致
- [ ] ⑦ `POST .../ai-report` → 返回 **501**（预期行为）

### 错误路径验收

- [ ] ⑧ 不存在的会话 → **404**
- [ ] ⑨ 重复提交 → **409**（幂等性生效）
- [ ] ⑩ `score: 99` → **400**，且 `fieldErrors` 指出问题字段
- [ ] ⑪ 空答案列表 → **400**

### 分数正确性抽查

用 `api.http` 里那组答案提交后，人工核对一遍开放性维度的计算：

| 题号 | 分值 | 是否反向 | 有效分 |
|---|---|---|---|
| 1 | 5 | 否 | 5 |
| 6 | 5 | 否 | 5 |
| 11 | 1 | **是** | 6-1 = 5 |
| 16 | 1 | **是** | 6-1 = 5 |
| | | **合计** | **20** |

原始分 20 → 归一化 `(20-4)/16×100` → **100.00**，档位「偏高」。

如果实际跑出来的开放性不是 100.00，说明计分链路有问题。

## 已完成：接入真实 AI

`DeepSeekAiReportGenerator` 已实现并通过真实 API 验证。

**做法回顾**（详细设计见 `docs/CODE_GUIDE.md` 第 9 节）：

- 提示词抽成独立的 `AiPromptBuilder`——**纯逻辑类，可单测，不联网不花钱**
- 两个实现用 `app.ai.enabled` 的**正反条件**互斥装配，保证容器里恰好有一个
- 事务边界：`读画像（短事务）→ 调大模型（事务外）→ 存报告（短事务）`
- 同一画像的报告默认缓存复用，`?regenerate=true` 才重新调用
- 上游故障返回 **502** 而不是 500——语义精确，便于排查方向

## V0.3 要补的东西

按优先级：

1. **React 前端**（`ResultResponse` 字段名已定死，静态页可直接当参照）
2. **用户登录**（`users` 表和 `test_sessions.user_id` 已预留）
3. **测试历史**（同一用户多次测试的对比）
4. **让 `rawScore` / `itemCount` 返回真实值**

   - 原因：`personality_profiles` 表只存了归一化分数
   - 修法：`buildResult` 里重新加载 answers + questions 再跑一遍 `ScoringService`

## 已知的取舍

**`rawScore` 和 `itemCount` 在结果接口里返回 `-1`。**

因为 `personality_profiles` 表只存了归一化分数，没存原始分。
要给出真实值得多查一次 `answers` 表并重新计分。
V0.1 判断这个附加信息不值得多一次查询，但**字段保留在 API 契约里**——
前端可以按最终结构写组件，V0.2 填上真值时前端不用改。

**每维度只有 4 道题，归一化后只有 17 个可能取值**（0、6.25、12.5、...、100）。

这是"别把量表搞复杂"和"分数要有区分度"之间的取舍。
V0.1 选择了从简，但 `ScoringService` 的 `itemCount` 是参数化的，
扩到每维度 6 题（25 个取值）只需要改数据，不动代码。

**题库未经心理测量学检验。**

信度、效度、项目区分度都没有做。题目是按语义直觉编写并分配维度的。
作为"自我探索 / 娱乐性质"的产品定位这是可接受的；
如果要做成严肃测评，需要重新设计并做统计检验。
